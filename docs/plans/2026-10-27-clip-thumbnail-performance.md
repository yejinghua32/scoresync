# 剪辑缩略图性能优化规划

## 背景与问题

笔记本电脑上使用剪辑页时 CPU 占用高，移动游标后当前帧图片出现慢。当前 `clip-editor.js` 一次展示游标前后各 4 帧，却从最前一帧开始串行等待 HTTP 请求；`loadThumbnail` 在 `FileReader.onload` 中才写入无上限的 `Map`，调用方未等待该回调，随后递归刷新可能重复请求。后端每个未命中的帧启动独立 FFmpeg，以宽度 320 的 PNG 输出；已有按资产 ID、大小和 mtime 命名的磁盘缓存，以及最多 2 个并发抽帧许可，但每个指纹目录仅按文件数清理，旧指纹目录不计入限额。接口发送 `Cache-Control: no-store`。逐帧索引构建和导出编码也可能占 CPU，需要在测量时与缩略图负载区分。

## 目标与成功标准

目标是降低剪辑页缩略图造成的 CPU 和等待时间，在笔记本上移动游标时优先看到准确的当前帧，且不牺牲逐帧选择及导出的精度。

1. 同一源指纹、帧号在并发请求和游标快速移动时不重复启动抽帧；当前帧优先于相邻帧，旧位置的预取不会堵住新位置的前台请求。
2. 正常步进时预取游标前方一小组帧，已经访问的附近帧可从有界内存缓存即时显示；以当前时间位置前后约 5 秒为保留窗口，同时设字节数上限，超限按最近使用情况淘汰。重新打开项目可复用有界磁盘缓存。
3. 缩略图采用比现有 PNG 更小的有损格式及限定分辨率；当前选中帧仍对应原始帧序号，不用邻近帧冒充。失败、源文件变化、越界和索引未就绪的现有行为保持一致。
4. 在同一台目标笔记本、同一源视频、同一冷/热缓存状态下记录优化前后指标：连续步进、跨段跳转各至少 30 次，观察当前帧显示延迟的中位数和 P95、FFmpeg 启动次数、Java/FFmpeg CPU 及缓存磁盘占用。目标是热窗口步进无需新 FFmpeg 进程，冷路径 P95 不高于基线，30 秒相同步进操作的 FFmpeg CPU 时间低于基线；如未达到，不能宣称性能问题已解决，须定位剩余瓶颈。

## 范围与非目标

包含：剪辑页缩略图请求调度、去重和内存淘汰；缩略图抽取格式、质量和线程/并发预算；源指纹磁盘缓存的全局容量与失效；定量对比和精确帧回归。

不包含：改变剪辑区间、逐帧索引、VFR 映射或导出内容；预先抽取完整视频/完整 5 秒的所有帧；因导出成功立即删除缓存；优化导出编码本身或记分编辑器；新增数据库表或依赖。

## 约束、确认与执行边界

- Spring Boot 3.2 / Java 17、外部 FFmpeg、纯 ES 模块。缓存目录是 `${SCORESYNC_DATA_DIR}/clip-cache`；缩略图仅经剪辑项目 ID 和帧序号访问，不能新增任意本地路径接口。现有源指纹校验和索引精确帧契约须保留。
- 用户提出降质、后续帧预取、约 5 秒内存缓存、磁盘缓存与跳帧等候选方向，并明确采纳“导出后保留磁盘缓存，到源视频变化或容量上限再清理”的推荐。精确当前帧来自现有剪辑功能契约；“只预取可见窗口附近，而非提前解码整段 5 秒”是控制笔记本 CPU/内存的设计选择，不是用户要求预先生成全部帧。
- 来源为 `brainstorming`。本会话只交付文档；实施由用户在新会话中使用 `subagent-driven-development` 启动，不在当前会话修改代码、运行时配置或提交。具体 JPEG 质量、内存/磁盘字节上限和抽帧线程数由执行者用基线测量及视觉检查确定，不能突破精度和有界资源要求。

## 关键方案

推荐分阶段优化现有按需抽帧管线：

1. 前端以当前帧为最高优先级；同一个帧号只有一个进行中的 Promise，图片解码/URL 建立完成才记为缓存命中；游标代次改变后停止旧队列的后续请求。少量并行加载可见邻帧，预取下一小组帧用更低优先级、受并发预算约束，不因每次 `timeupdate` 扩张队列。缓存使用 Blob/Object URL 或等效可释放资源，按视频时间附近约 5 秒与总字节预算双重约束淘汰，并释放 URL；切换项目/卸载页面时清理。
2. 后端对同一指纹帧的同时请求合并生成，继续先校验源文件；使用有限宽度的 JPEG/WebP 等浏览器兼容格式（优先 JPEG），固定并测试质量和实际体积，响应 MIME/缓存扩展名一致。抽帧进程及解码线程限制需在真实样片上权衡单帧延迟与 CPU；前台请求不应被大量后台预取占满。新格式加缓存版本键，避免旧 PNG 被当作新响应。
3. 现有磁盘命中继续跨页面/导出复用；从“每指纹目录 600 个文件”改为所有指纹目录共享的有界容量策略，能清理陈旧指纹，保护当前写入和进行中的读请求。源文件变化仍拒绝旧项目继续编辑，不使用旧图作为新源内容。导出成功、失败或取消不以清理缩略图作为副作用。

备选方案：

- 一次 FFmpeg 进程批量解码相邻帧可降低进程启动和重复 seek 成本，但需核对 GOP、VFR、时间戳与解码帧序号，且长批次可能抬高 CPU 峰值。若上述方案经测量仍受重复解码主导，再作为单独增量，先用真实 CFR/VFR 样片验证逐帧一致性。
- 用浏览器视频画面 `canvas` 捕获或用跳帧/稀疏采样代替所有缩略图可减少服务端抽帧，却依赖浏览器 seek 精度；仅可考虑给远离当前帧的辅助预览使用，不能代替当前帧或改变导出边界。本次不采用。

## 实施计划

### 任务 1：当前帧优先与有界前端缓存

- **范围**：`src/main/resources/static/js/clip-editor.js`，必要时剪辑页局部呈现及 `StaticPageIntegrationTest`。
- **实施要点**：先给当前帧发起或复用请求，再填可见邻帧，低优先级预取游标前方的一小组帧；消除 `FileReader` 回调与递归刷新的竞态，按代次丢弃过时结果，限制进行中请求数量。缓存以实际字节计量并淘汰，窗口按 `frameTimes` 的时间戳而不是固定帧数确定，以覆盖 VFR；不为 5 秒内每帧主动启动 FFmpeg。错误帧允许重试，不保留永久失败 Promise。
- **完成条件**：热缓存步进不再发请求，快速跳转后新当前帧不会排在旧位置邻帧之后；长时间编辑内存不持续增长。
- **待执行验证**：`mvn "-Dtest=StaticPageIntegrationTest" test`；浏览器网络面板检查相同帧无重复请求、切换游标和项目时占用回落。

### 任务 2：轻量图像与后端同键合并

- **范围**：`src/main/java/com/scoresync/service/render/ClipFrameExtractor.java`、`ClipThumbnailService.java`、`src/main/java/com/scoresync/web/ClipProjectController.java`、`src/main/java/com/scoresync/config/AppProperties.java`、`src/main/resources/application.yml`；对应 `ClipThumbnailServiceTest` 和 `ClipProjectApiIntegrationTest`。
- **实施要点**：以受控有损格式输出缩略图，更新响应 MIME、缓存版本/扩展名；维持源文件指纹和帧范围检查。对同一键的并发未命中复用一个结果/写入，避免多个线程争用相同 `.tmp`；进程/线程预算使后台预取不抢占当前帧。若服务端无法识别请求优先级，可先在前端严格限流并预留前台抽帧容量，不开放任意路径参数。
- **完成条件**：同键并发只抽一次；内容类型正确；旧 PNG 不误用；源变化、失败、中断和越界可恢复；真实样片选中帧与原帧对应。
- **待执行验证**：`mvn "-Dtest=ClipThumbnailServiceTest,ClipProjectApiIntegrationTest" test`；真实短片比较 PNG/JPEG 字节数、画质与单帧耗时，含 VFR 和无音轨视频。

### 任务 3：磁盘缓存容量与生命周期

- **范围**：`ClipThumbnailService.java` 及其测试；仅在需要时抽取同目录的内部缓存辅助类。
- **实施要点**：按所有源指纹目录的实际字节总量实施容量上限和最近使用淘汰；从命中也维护可用于淘汰的使用时间，避免每次写入都全量扫描大量文件。失效版本/旧源目录可安全回收，但不删除帧索引、源视频、导出文件或正在使用的临时文件。没有必要把缩略图写进 SQLite；导出生命周期不触发清理。
- **完成条件**：跨多个项目/指纹累积仍有磁盘上限；重开项目、导出后可复用未淘汰的图；容量清理不影响正在进行的读取或生成。
- **待执行验证**：`mvn "-Dtest=ClipThumbnailServiceTest" test`；临时缓存目录测试多指纹、触顶、读后保留和生成并发。

### 任务 4：同机验收与结果归因

- **范围**：测试与必要的简短测量记录；不修改剪辑/导出数据语义。
- **实施要点**：先在实现前采集同机基线，分开记录首次建索引、纯缩略图浏览和导出；以同一视频、同一路径操作、冷/热缓存各一轮复测。区分浏览器渲染、Java 和 FFmpeg 的 CPU。若真实瓶颈仍在索引或导出，记录不属于本次缩略图优化的剩余工作，不以提高预取并发掩盖。
- **完成条件**：成功标准中的请求次数、延迟和 CPU 对比可复核，精确帧和导出回归通过；不满足指标则继续定位或明确留下未解决项。
- **待执行验证**：`mvn test`；使用显式临时 `SCORESYNC_DATA_DIR` 和真实 FFmpeg 手测短片、长片、VFR、重新打开与导出后复用。仓库自动测试不调用真实 FFmpeg。

## 顺序、风险与恢复

任务 4 的基线采集先于修改，之后依次完成 1、2、3，最后复测 4。执行会话建立总体目标及完整清单；每阶段核对网络请求、缓存占用与帧准确性，最终检查 diff、运行风险相称验证，并按仓库规则通过 `git-handoff` 创建聚焦本地提交（除非不满足安全提交条件）。

预取多了会抬高 CPU，图片太模糊会损害帧辨识，缓存过大可能挤占笔记本内存/磁盘；用小窗口、字节预算、前台优先级和真实画质检查控制。新缓存格式应以版本目录自然隔离旧图；回退代码后仍可重建旧格式缓存，不迁移 SQLite。开放项：无必须由用户决定的行为问题；具体预算值由测量确定并记录。
